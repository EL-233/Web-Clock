## v4 — 2026-10-02

`clock-site_v4_2026-10-02.zip`　（5 个文件，约 641 KB，压缩后 290 KB）

**这一版不改时钟长什么样**（100% 时三种样式的渲染结果与 v3 逐位一致），
改的是**界面本身的两条底层规范**，外加第一个"数值型"设置。

**起因**：三套样式大小不同是设计（每套各自撑满屏幕），但**设置面板也跟着变**——
同一个面板在 v1 下宽 463px、在 v3 下宽 671px，差 45%。这是缺陷不是设计。
而且用户预告后面要加很多设置（单独模块大小调节等），v3 那种单列长列表再加几行就装不下了。

### 规范一：界面尺度与内容尺度解耦（本版最重要的一条）

| | 用什么单位 | 跟什么变 | 为什么 |
|---|---|---|---|
| **内容**（时钟卡片 / 文字栏 / 走秒带） | `rem` | 根字号 → **随样式变** | 每套样式要各自撑满屏幕，这是设计意图 |
| **界面**（设置面板 / 齿轮 / 按钮） | **`px`** | 只跟屏幕像素 | 界面不该被内容尺度绑架 |

根因：`layout()` 改的是 `document.documentElement.style.fontSize`（**根字号**），
而面板、齿轮、按钮全都写在 `rem` 里 —— 根字号随样式变，界面就被一起拖着变。
**同一份根字号被两种用途复用了**，这是问题所在。

所以 `.gear` / `.panel` 及其内部**所有规则里的 `rem` 全部换成 `px`**，内容部分一律不动。
现在面板宽度是恒定的 **300px**，任何样式、任何倍率下都不变。

> iPad 2 是固定设备（1024×768 / 768×1024），固定像素完全可预测。
> 界面用固定像素本来就比用视口单位合理 —— 界面不该在小屏上缩水。

**界面设计令牌（全部 px）**

| 类别 | 值 |
|---|---|
| 间距 | 4 / 8 / 12 / 16 |
| 圆角 | 面板 6 · 按钮组与按钮 4 |
| 字号 | 标签 14 · 按钮与标签页 13 |
| 行高 / 标签页高 | 34 |
| 面板 | 宽 300 · 内边距 12 · 距上 54 · 距右 6 |
| 齿轮 | 热区 44×44（手指舒适尺寸）· 距角 6 · 图标三条线：宽 20 高 2 间距 5 |

### 规范二：面板结构 = 右上角弹层 + 分页 + 两种控件

不再是一个长列，改成**标签页 + 分页**，每页短平，以后往对应页里追加：

| 页 | 设置项 |
|---|---|
| **外观** | 卡片样式（平衡/层次/走秒）· 主题（深色/浅色）· **大小**（本版新增） |
| **时间** | 小时制（24/12）· 冒号（开/关） |
| **天气** | 数据源（实时/示例/离线）· 自动主题（开/关） |

> 冒号归「时间」而不是「外观」：它是**秒的指示器**，按功能分页比按视觉分页好找。
> 当前页记在 JS 变量里（不持久化），重开面板停在上次那页。

**控件词汇 —— 以后加设置只准用这两种，不要每个功能发明一个新控件：**

1. **分段选择**（`.seg`）—— 枚举型，2–4 个互斥选项
2. **步进器**（`.step`，`− 值 +`）—— 数值型

**行结构恒为「左标签 + 右控件」**，加功能时行本身不用再动。

### 新增：每套样式独立调大小

外观页一行「大小」，步进 5%、范围 **70%–120%**，**每套样式各自记值**（`sizeMul: {v1,v2,v3}`），
切样式时那一行显示对应样式的值。100% = 现在这套观感，一点不变。

**必须处理的上限**：放大可能把内容顶出屏幕，而三套样式的安全余量并不一样 ——
**v3 本来就已经吃到高度上限的 94%**，几乎没有余量；v1/v2 还有约 18%。

所以 `layout()` 里加了一道**硬性夹取**：先按样式算理论字号 → 乘用户倍率 →
再用"内容实际占位"反算的上限夹一下，**保证永远不溢出**：

```
上限 = min( 屏宽 × 0.94 / 该样式内容宽 , 屏高 × 0.94 / 该样式内容高 )
```

各样式的内容占位是已知常量（`FOOTPRINT`），直接写进代码。实测：

| 横屏 1024×768 | 100% 字号 | 理论上限 | 请求 120% 时实际 |
|---|---|---|---|
| v1 平衡 | 59.4px | 73.6px | **120.0%** |
| v2 层次 | 68.6px | 86.1px | **120.0%** |
| v3 走秒 | 86.0px | 93.5px | **108.6%** ← 被夹住 |

| 竖屏 768×1024 | 100% 字号 | 理论上限 | 请求 120% 时实际 |
|---|---|---|---|
| v1 平衡 | 44.5px | 55.2px | **120.0%** |
| v2 层次 | 51.5px | 64.6px | **120.0%** |
| v3 走秒 | 66.0px | 70.1px | **106.1%** ← 被夹住 |

> ⚠️ **v3 到不了 120% 是刻意的，不是 bug。** 以后看到"倍率失灵"先看这张表。
>
> 夹取放在 `layout()` 里而不是放进步进器的可选范围：上限随**横竖屏**变化，
> 而倍率是全局设置。放在 `layout()` 里每次重算，才不会被旋转屏幕绕过。

### 验证

机械断言（脚本扫源码，比肉眼看可靠）：

- `.gear` / `.panel` / `.tabs` 及其子元素的规则里**不允许再出现 `rem`** —— 有任何残留即失败。
  这是"界面不再随样式变"的**机械保证**。→ 通过（内容部分仍有 120 处 `rem`，未动）
- 100% 时三种样式的根字号**与改动前逐位一致**（59.39 / 68.61 / 86.02 / 44.54 / 51.46 / 66.05）→ 通过
- 三个标签页、`data-tab` 与 `data-page` 一一对应、7 个设置的 `data-k` 各出现一次 → 通过
- 步进器到 70% / 120% 端点后不再变化；三套样式倍率互不干扰 → 通过

**真机待验**（下次拿 iPad 时确认）：齿轮热区好不好按、标签页切换跟不跟手、
面板边缘会不会被状态栏遮、面板打开时会不会压到时钟。

### 改代码前必读

1. **界面写 `px`，内容写 `rem`。** 新加设置项时，面板里的任何尺寸都别用 `rem` ——
   一旦用了，那个元素就会跟着样式变形，而且很难一眼看出是这个原因。
2. **新加设置先问"这归哪一页"**，再问"用分段还是步进器"。页放不下就新开一页，
   不要把行挤小。
3. **`FOOTPRINT` 是手工量出来的内容占位**，改动卡片 / 环盒 / 文字栏的尺寸后要同步更新，
   否则夹取会算错（改小会白夹，改大会溢出）。

### v4.1 — 2026-10-02

`clock-site_v4.1_2026-10-02.zip`　（5 个文件，约 641 KB，压缩后 290 KB）

v4 的小改：**走秒样式的时间和日期略往上**；**天气整栏小一号**（为以后加天气信息腾地方）。
不涉及架构，两条规范都不变。

**1. v3 的竖向定位改了推导方式** —— 从"把时钟摆到正中"改成"整组居中"

原来是 `padding-top:.50rem` 把内容下推、好让**时钟落在屏幕正中**。现在归零，
让**整组居中**，时钟就自然落在中心上方 —— 因为时钟下方比上方多一栏天气：

```
日期栏 .83 → 间距 1.0 → 时钟 2.88 → 间距 1.0 → 天气栏 1.22   合计 6.93rem
时钟中心距组顶 = .83 + 1.0 + 2.88/2 = 3.270rem
组半高 = 6.93/2 = 3.465rem  →  时钟比组中心【高】.195rem
```

实际位移：横屏 ≈17px、竖屏 ≈13px（"稍微往上"）。归零的好处是不用再维护一个
"补偿系数"——时钟偏高现在是从版面结构里**自然推出来**的，不是凑出来的。

**2. 天气栏整体小一号**（v1 是独立单行排版，未动）

| | 从 | 到 |
|---|---|---|
| 当前温度 `.wx-main` | .54rem | **.48rem** |
| 高低温 / 未来1小时 `.wx-extremes` `.wx-next` | .44rem | **.40rem** |
| 对应行高 | .58rem | .52rem |
| 天气栏高度 `.bar--weather` | 1.33rem | **1.22rem** |
| 雨图标 / 冷热箭头 | .32×.22 / .13 | **.30×.20 / .12** |

> ⚠️ 字号写在 `.wx-main` 上，**没有动 `.bar` 的 .54rem** —— `.bar` 同时管着**日期栏**，
> 动它日期会跟着缩。层级也保住了：当前温度 .48 仍大于右两栏的 .40。
> 图标同步缩了 ~9%，否则字号小了图标会显得发胖。

**3. 为"以后显示更多天气"留的余地**

- 天气栏**高度**是 v3 的竖向主导量，**宽度**（10.30rem）更是 v3 缩放上限的决定因素 ——
  它比环盒 9.42rem 还宽，**往横里加栏位会直接压小时钟**。
- 所以加行（往下长）比加栏（往横长）安全。**但一处加了三处要跟着重算**：
  CSS 的 `.bar--weather` 高度 / v3 的 `.stage` padding 推导 / JS 的 `FOOTPRINT`。
  这三处现在都写了交叉引用的注释。

**验证**：脚本从 CSS 反推几何，与 JS 的 `FOOTPRINT` 对账 —— 这次真抓到一个错
（v3 的 `h` 我误留了早先草稿里 `padding-top:.20rem` 的残留，7.13 应为 **6.93**）。
同时确认 100% 时六种情况的根字号**一位没动**（59.39 / 68.61 / 86.02 / 44.54 / 51.46 / 66.05），
即**时钟大小完全没变**；三种样式的缩放上限也没变（仍由宽度决定）。

### v4.2 — 2026-10-02

`clock-site_v4.2_2026-10-02.zip`　（5 个文件，约 642 KB，压缩后 292 KB）

新增**「走带」**设置：**关 / 连续 / 脉冲**。只对走秒样式有意义，其余样式下不生效。
默认「连续」= 改动前的行为，一点没变。

**放在「时间」页**（和冒号同一页）：两者是同一类东西 —— **秒的指示器**，
沿用 v3 定的「按功能分页」原则。三个选项让它落在 3 行，正好与「外观」页等高，
所以三个标签页都是 102px —— **切标签页面板高度不跳**。

| 模式 | 行为 |
|---|---|
| 关 | 整条隐藏。**环是绝对定位、不参加 flex，所以隐藏它不会让时钟变大** |
| 连续 | 用小数秒，均匀推进（本文件从前只有这一种） |
| 脉冲 | 一秒走一格，但那一格是缓入缓出的 |

关掉走带后，若冒号也关掉，**整条 rAF 帧循环会停掉** ——
这是这台设备上唯一持续烧 CPU 的地方，能停就停。

**脉冲的数学（本版唯一有讲究的地方）**

缓动直接复用冒号的 `smoothstep`，窗口也取**同一个 `RAMP`（0.18 秒）** ——
这就是"和冒号同一种非线性程度"。

> ⚠️ **缓动段只能落在整秒【之内】，不能像冒号那样跨在整秒两侧。**
> 环的位置必须**单调不减**（它是进度，不能倒退），且每秒正好前进 1/60，
> 于是"缓动百分比"必须每秒从 0 走到 1。若让它跨过整秒 ——
> 整秒那一刻 n 会 +1、而缓动值还停在 0.61，位置瞬间跳掉 1/60，
> **那就成硬切了，反而不"非线性"**。
>
> 所以只有两种落法，这里取**"整秒之前"缓动**，两个理由：
> 1. **与冒号对得更齐。**眼睛感知到"变了"是在缓动到 `ALIGN_T`（0.61）那一刻。
>    取后者：落在整秒**前 0.0702 秒**；取前者：整秒**后 0.1098 秒**，差 56%。
> 2. **整分回绕好看得多。**第 59 秒的缓动恰好把环推到**满圈**，紧接着 `ring-flash`
>    播满圈淡出 ——「走满 → 闪一下 → 归零」一气呵成。若取前者，环会在第 59 秒
>    **开头**就跳满，然后干等 0.8 秒。

**验证**（脚本照抄实现逐点验算，每秒 1000 个采样点）：

| 断言 | 结果 |
|---|---|
| 每个整秒处，环的值**精确**等于真实秒数 | 最大误差 0.0e+00 |
| 整分钟单调不减（进度不倒退） | 通过 |
| 每个整秒处连续（没有硬切） | 最大跳变 1.1e-16 秒 |
| 一分钟正好走满一圈（不会越走越偏） | 60.0000 / 60 |
| 连续模式原样返回（改动前行为不变） | 通过 |
| 关掉走带不改尺寸（FOOTPRINT / 根字号系数未动） | 通过 |

### v4.3 — 2026-10-02

`clock-site_v4.3_2026-10-02.zip`　（5 个文件，约 642 KB，压缩后 292 KB）

脉冲"太生硬"，把缓动窗口从 **0.18 秒拉长到 0.36 秒**，
即 `RING_RAMP` **与冒号的 `RAMP` 解耦** —— 同一条 smoothstep 曲线，但窗口不再共用。

**为什么必须解耦**：环一格的位移比冒号大得多（1/60 圈，横屏约 36px）。
smoothstep 的峰值斜率是 1.5，所以 **峰值速度 ÷ 连续模式速度 = 1.5 ÷ 窗口**（与一格多长无关，换屏幕也成立）：

| 窗口(秒) | 占一秒 | 停顿(秒) | 峰值速度 | ÷ 连续模式 | 感知点距整秒 |
|---|---|---|---|---|---|
| 0.18 | 18% | 0.82 | 300 px/s | **8.3 倍** | 0.070 秒 |
| 0.25 | 25% | 0.75 | 216 px/s | 6.0 倍 | 0.098 秒 |
| **0.36** | **36%** | **0.64** | **150 px/s** | **4.2 倍** | **0.140 秒** ← 现在 |
| 0.45 | 45% | 0.55 | 120 px/s | 3.3 倍 | 0.176 秒 |
| 0.50 | 50% | 0.50 | 108 px/s | 3.0 倍 | 0.195 秒 |

> 「生硬」的量化解释就是那 8.3 倍 —— 峰值速度是连续模式的八倍多，看着就是"啪"地弹一下。
> 拉到 0.36 后降到 4.2 倍。**要继续调就动 `RING_RAMP` 一个常量：**
> 往 0.45 调更灵动，往 0.25 调更干脆；拉过 0.5 就快看不出是"一格一格"了。

**代价**：与冒号的对齐松了一些 —— 感知点距整秒从 0.070 秒变成 0.140 秒
（距离 = 0.39 × 窗口，窗口越长越松）。这是没法两全的：
缓动段只能落在整秒之内（原因见 v4.2），窗口一长，感知点就必然离整秒更远。

**踩到的坑（我的错，不是文件的错）**：v4.2 的注释里我把这个比值写成了"5.5 倍 / 2.8 倍"，
是**算错的**。正确是 1.5 ÷ 窗口 = 8.3 倍 / 4.2 倍。这一版已改正。
教训：这种"倍率"说法一定要用脚本算一遍再写进注释 —— 肉眼估的倍数最容易错。

**验证**：改窗口没有破坏 v4.2 验过的任何性质 —— 整秒处取值仍精确等于真实秒数（误差 0）、
整分钟单调不减、整秒处连续（跳变 0）、一分钟正好走满一圈。峰值速度降 50%。

### v4.4 — 2026-10-02

`clock-site_v4.4_2026-10-02.zip`　（5 个文件，约 643 KB，压缩后 293 KB）

脉冲的缓动曲线换成**微软 Fluent 那套**，并且**落法（整秒前 / 整秒后）跟着翻**。

**曲线出处**（两个官方来源互相印证，都是实查的，不是凭记忆）：

| 来源 | 曲线 |
|---|---|
| Microsoft Learn《Timing and easing》 | 入场 `cubic-bezier(0, 0, 0, 1)` · 退场 `cubic-bezier(1, 0, 1, 1)` |
| Windows《Motion in Windows》表 | **已有元素点到点 = `cubic-bezier(0.55, 0.55, 0, 1)`** ← 取这条 |
| Fluent 2 `@fluentui/tokens` | `curveDecelerateMid` = `(0,0,0,1)` · `curveDecelerateMax` = `(0.1,0.9,0.2,1)` 等 |

走带是"**已有元素在界面内移动一小段距离**"，正好对应表里 Point to Point 那一行。

**为什么不取那条更有名的 `cubic-bezier(0, 0, 0, 1)`**：它的起始斜率**发散**
（化简后 `Y = 3x^(2/3) − 2x`，`x→0` 时导数趋于无穷）。设计意图是"元素从很远处高速冲进场景"，
出场距离越大越好看；而走带一格只有 36px，用它**第一帧就要吃掉 29% 的位移（约 10.6px）**——
那不是灵动，是闪。现用曲线第一帧只吃 4.9%（约 1.8px）。

**这条曲线的实测特征**（脚本采样 2000 段）：

| | |
|---|---|
| 起始斜率 | **1.0**（= y1/x1，有限 → 不会第一帧跳一大截） |
| 速度峰 | 窗口 **30%** 处（smoothstep 是 50%） |
| 终点斜率 | **0**（末控制点 (0,1) 决定切线水平 → 平顺落位） |
| 前 1/3 窗口走完 | **71.3%** 的位移（减速型 = 前重后轻） |

**落法必须跟着翻**（这是本次最容易被漏掉的一步）：

> 缓动段只能整个落在**一个整秒之内**（原因见 v4.2），所以只有"整秒之前"和"整秒之后"两种落法。
> 选哪种，取决于**曲线的速度峰在窗口的哪个位置** —— 目标是让"位移最明显的那一刻"贴住整秒
> （整秒正是冒号呼吸里被对齐的瞬间）。
>
> | 曲线 | 速度峰 | 该用的落法 | 感知点 |
> |---|---|---|---|
> | smoothstep（v4.3） | 正中 50% | 整秒**之前** | 整秒**前** 0.140 秒 |
> | 微软点到点（现在） | 前段 **30%** | 整秒**之后** | 整秒**后** 0.108 秒 |
>
> **不翻的话**，感知点会跑到整秒**前 0.252 秒**，和冒号明显脱节。

落成"整秒之后"的代价：环走完一格后会停在**新值**上等大半秒，
整分时表现为"满圈停住 → 闪一下 → 归零"（可以接受：环本就只是"暗示"，
与冒号对齐比绝对精确更重要）。好处是顺带修掉了 v4.3 的一个小毛病 ——
整秒之前落法下，第 0 秒有 82% 的时间 `drawn=0`，会触发"发丝线"隐藏逻辑。

**验证**（照抄实现逐点验算）：

| 断言 | 结果 |
|---|---|
| 自写的贝塞尔求值器 vs 60 次二分参考解（400 采样） | 最大偏差 3.06e-06 |
| 起始斜率有限（1.001），对比入场曲线的发散（≈644） | 通过 |
| 每个整秒处取值精确 = 真实秒数 | 误差 0.0e+00 |
| 整分钟单调不减 / 整秒处连续 / 一分钟走满一圈 | 通过 |

> 求值器用**二分**而非牛顿：这条曲线在 s=1 处斜率恰为 0（末控制点 (0,1) 让切线水平），
> 牛顿会在那里除零。二分没这个问题，18 次迭代精度 1e-6 —— 折算到 36px 上是 0.0004px。

**又抓到我自己一个错**：我先把速度峰写成"窗口开头"，还据此写了整段理由。
实测发现峰在 30% 处。手算时只取了 s=0 和 s=0.5 两个点，都没找到极值就下了结论。
**教训同 v4.3：这类"形状特征"必须用脚本扫一遍再写进注释。**

### v4.6 — 2026-10-02

`clock-site_v4.6_2026-10-02.zip`　（5 个文件，约 645 KB，压缩后 297 KB）

「走带时长」步进器**改成横向滑杆**，范围从 150–600ms **放宽到 60–1000ms**。
关键在于：滑杆改的**不只是时长，还有曲线**。

**一个想通了才做得对的点：脉冲最松弛的那一端，恰好就是"连续"。**

用户说"松弛的时候甚至能接近匀速"。而匀速 = 窗口占满一秒 + 曲线线性。
也就是说，**「脉冲」和「连续」本来就是同一根轴的两端**，不是一个开关的两侧。
所以滑杆左端是瞬切、右端平滑地变成连续 —— 到 1000ms 时两者**逐点相同**
（实测偏差 1.9e-06）。

**曲线为什么也必须跟着变**

微软曲线把约 71% 的位移压在窗口的前 1/3。窗口短时那是"果断"；
窗口一长（800ms 的前 1/3 = 270ms）就变成"猛地一顿、然后慢慢爬"，不像一个整体动作。
所以曲线在 `cubic-bezier(0.55,0.55,0,1)`（微软点到点）和
`cubic-bezier(1/3,1/3,2/3,2/3)`（**精确线性** —— 化简后 `B(s)=s[(1−s)+s]²=s`）之间插值：

```
blend = (时长 − 360ms) / (1000ms − 360ms)    钳到 0..1
```

> ⚠️ **插值从 360ms 才开始**，不从下端开始。360 是默认档；
> 若从下端就插值，用户会把滑杆停在默认位置，却"什么都没动、手感却变了"。
> 定在这一档上，**默认档的观感与 v4.5 完全一致**（实测 12.0 倍 vs 前一版的 12.3 倍，
> 差异来自 360→363ms 的取整）。

**滑杆位置用几何映射，不用线性**

范围跨了两个数量级（60→1000ms，16.7 倍）。线性映射会把紧绷端全挤在最左边 15%，
根本没法调。人对时长的感知本来就是**对数**的 —— 150→300ms 和 300→600ms 一样明显，
后者在线性轴上却要占两倍宽度。几何映射让每拖一格改的是固定**倍率**（约 2.9%），
手感才均匀；副作用是 150ms 正好落在 1/3 处、360ms 落在 2/3 处，都好找。

| 滑杆 | 时长 | 停顿 | 峰值速度 | ÷连续 | 走完 90% | 前 1/3 窗口走完 |
|---|---|---|---|---|---|---|
| 0% | 60ms | 0.94s | 2653 px/s | 73.7 倍 | 28ms | 71% |
| 33% | 152ms | 0.85s | 1047 px/s | 29.1 倍 | 70ms | 71% |
| **64%** | **363ms** | **0.64s** | **433 px/s** | **12.0 倍** | **169ms** | **71%** ← 默认 |
| 80% | 570ms | 0.43s | 144 px/s | 4.0 倍 | 366ms | 53% |
| 95% | 869ms | 0.13s | 52 px/s | 1.4 倍 | 732ms | 38% |
| **100%** | **1000ms** | **0.00s** | **36 px/s** | **1.0 倍** | 900ms | 33% ← = 连续 |

（横屏 v3，一格 ≈ 36px；连续模式 = 36 px/s。最后一列从 71% 平滑降到 33%，
就是曲线在往线性走的证据。）

**控件用原生 `input[type=range]`，不是自绘 div**

原生自带完整的触摸拖动行为 —— 手指划出元素范围也不丢、划多快都不掉，
这些自己实现很容易有边角问题。iOS 9 上 `-webkit-appearance:none` 之后
轨道和滑块都能完全自定样子。**输入框本体 + `::-webkit-slider-runnable-track` +
`::-webkit-slider-thumb` 三处都要写 `-webkit-appearance:none`**，少一处就退回系统外观。

拖动中**不写 localStorage**（iOS 的 localStorage 是同步的，拖动时每帧写会在 A5 上卡），
存盘放到松手（`change`）时做。拖动时也**不回写滑杆自己的 value** ——
值→位置→值 一来一回可能差一格，会和手指抢滑块。

**验证**（照抄实现逐点验算）：

| 与「连续」模式逐点比对 | 最大偏差 1.88e-06 |
| 95 档（60–1000ms 每 10ms）：整秒处精确 / 单调不减 / 整秒处连续 | 通过 |
| 位置→时长→位置 精确回到原格（拖动时滑块不自跳） | 最大误差 0 格 |

| 松弛端手感 | 一拖就跳 30ms | 每格都看得出来 |
| 滑杆取值 | 0–100（需换算） | **直接是毫秒** |

> 撤掉几何映射的代价是失去"对数均匀"的手感。但 20ms 这个粒度已经够细，

**`clampRingMs` 现在会把值归到步进网格**（`60 + n×20`）——
这样手改过的 localStorage 也不会让滑块停在两格之间。

**ⓘ 一个还没解决的残留问题（先说清楚）**

47 格摊在约 186px 宽的滑杆上，**每格约 4px**。手指想精确落到某一格仍然吃力 ——
20ms 步进解决的是"两端疏密不均"，不是"总格数太多"。

**交互**

- 右上角一个 `.5rem` 的小图标（三条带旋钮的横线，纯 CSS 画），
  但**触摸热区 1.6rem**，不用瞄准

- 面板收起时**整页只有那一个热区响应触摸** —— 这是对 v2「误触」顾虑的处理：
  把可误触面积压到最小，而不是靠隐式长按手势

**几个刻意的决定**

- **不用 CSS 变量做主题**。查证结果：iOS 9.3 = Safari 9.1，CSS 变量只是
  「部分支持」，有 `calc()` 嵌套的已知 bug。而本项目要覆盖的颜色本来就只有十来个，
  class 方案（`body.light .half {...}`）零风险。
- **`localStorage` 先做可写性探测**。iOS 无痕模式配额为 0，`setItem` 会抛
  `QuotaExceededError`。存不住就退回内存默认值 —— 设置记不住可以接受，
  但它绝不能把时钟搞挂。
- **`visibilitychange` 带 webkit 前缀**。iOS 9 上事件名和 `document.hidden` 都可能带前缀，
  代码里做了特性检测兼容两种写法。
- **两套样式的基础值直接按 v2 写死，不挂在 `body.style-v2` 上**。
  这样万一 JS 挂了、body 上没加上类，页面仍按 v2 正常渲染。
- **天气两套排布都写在 DOM 里、都填数据**，切样式只切显示 —— 不重新请求、不闪。
- **透视保持在长焦 `20rem`，不随样式回退**。广角是 v1 的**缺陷**不是风格，
  回到 v1 样式时把缺点一起带回来不合理。

**偏离计划的一处（已按更优解处理）**

计划里写的是「两套样式共用同一个根字号系数」，实现时改成了**分别取值**
（v2 `0.067w` / v1 `0.058w`）。原因：v1 的卡组宽 17.6%（13.68rem vs 11.63rem），
统一取值就必须迁就 v1，会让 v2 被迫缩小 12% —— 而 v2 正是当前在用的外观。
分别取值的代价是切换样式时数字尺寸变约 15%，但两套外观本来就整体不同，
且这样每套都能撑满屏幕。

**归档后修掉的一个 bug —— 桌面鼠标点不动**

第一版面世时，齿轮挂了 `click` 兜底，但**面板内的选项按钮和「点外部关闭」只有 `touchstart`**。
结果：桌面上齿轮能点开面板，但点任何选项都没反应、点外面也关不掉；iPad 上一切正常。

改成统一的 `bindTap()`：同时挂 `touchstart` 和 `click`，用时间戳去重 ——
触摸设备上 `preventDefault` 通常会挡掉合成 click，但各家行为不完全一致，
留一道 700ms 的保险，免得开关被切两次。
另外「点外部关闭」刻意**不** preventDefault：它只是旁观，不该影响页面其他默认行为。

⚠️ 教训：**「在 iPad 上测过」不等于测过**。这个项目的主战场是 iPad，
但开发预览在电脑上，两条输入路径都得覆盖 —— 只覆盖一条，另一条在真机上才暴露。

**归档后的三处微调**

1. **天气读不到时用 `-` 占位**。四个槽位的初始内容直接写死在 HTML 里就是 `-`，
   所以拿到数据之前、以及从头到尾都没拿到数据时，界面结构仍完整可见。
   拿到过数据之后再失败则**保留上一次的值** —— 陈旧数据也比丢掉信息强。
   （即：`-` 只在「从来没有过数据」时出现，不是每次失败都刷成 `-`。）
2. **设置图标改小、去掉滑块旋钮**，就三条细横线（线宽 `.62rem → .40rem`）。
   触摸热区仍是 1.6rem，只是看不见，所以线虽细也好点。
3. **面板放宽、行高加大**：宽 `6.6rem → 7.8rem`，行高 `.72rem → .98rem`，
   按钮内边距也加了一档 —— 原来标签和按钮挤在一起。

**再增第三档样式：走秒带**

在 v2 基础上拿掉秒卡、时+分居中，外缘套一圈走秒的环。
进度 = 本分钟已过秒数 / 60，用 SVG 的 `stroke-dasharray` / `stroke-dashoffset` 做。

- **环的路径用显式 `<path>`，不用 `<rect>`**。`<rect>` 的虚线起点固定在左上角
  （`x+rx, y`），想挪到顶部中点得靠 `stroke-dashoffset` 反向补偿一段 ——
  符号方向容易搞反，而且离线没法验证。显式写成「从顶部中点出发、顺时针绕一圈、
  回到顶部中点」（`M500 6.5 … H500`）就把起点钉死了，零歧义。
- **周长用 `path.getTotalLength()` 取**，取不到回落到手算值 `2654`
  （圆角矩形周长 = 2(w+h) − 8r + 2πr = 2(987+387) − 8×55 + 2π×55 ≈ 2654）。
  **不用 `pathLength="60"` 这种简写**：Safari 9 对 `pathLength` 的支持没把握，
  万一不支持，`dasharray` 会被按用户单位解释，环直接坏掉。
- 描边 `13` 单位 = `0.13rem`，环内侧距卡片外缘 `0.30rem`；
  环盒 `10rem × 4rem` = 卡组 `9.12rem × 3.1rem` + 两侧各 `0.44rem`。
- `stroke-linecap="butt"` 而非 `round` —— round 在进度为 0 时仍会画出一个圆头点。
- 只在「秒数变了」时才写属性（`lastRingS` 闸门），不是每 250ms 的 tick 都写。

**顺带修掉一个潜伏的 bug**：`.clock` 缺 `position:relative`。
它是 v2 重写时被拿掉的（当时没有东西需要它）。走秒带是绝对定位，
没有这个基准就会上溯到 `.stage`，而 stage 居中的是「时钟 + 上下文字栏」整组，
环会垂直错位 —— 上机看一眼就会发现的错，但静态检查抓不到，是我写方案时才意识到的。

**走秒带的四轮打磨**

1. **改成无极连续**。原先由 250ms 的 `tick` 驱动、每秒跳一格。改成用**小数秒**
   （`getSeconds() + getMilliseconds()/1000`），由独立的 `setInterval(…, 50)` 约 20fps 驱动。
   环每秒只走 1/60 圈，20fps 下每帧推进 1/1200 圈，看不出台阶。
   **不用 v3 样式时该函数立即返回**，不做任何计算 —— 连续刷新的代价只在选中它时才付。
2. **描边变细**：13 → 9 单位（0.13rem → 0.09rem）。
3. **修正四边间距 —— 这条不是调数值，是圆角半径算错了。**
   环的圆角必须取 `卡片圆角 + 间距 + 半描边` = 42 + 30 + 4.5 = **76.5**，我原来给的是 55。
   半径给小了，四个角会向内收紧：**直边处间距正常、拐角处却更窄**，
   看上去正是"上下左右不一致"。修正后环盒 `9.9rem × 3.88rem`，
   减去卡组 `9.12rem × 3.1rem` 与描边，**左右与上下的净间距都是 0.300rem**。
   （校验脚本把这条写成了可计算的断言，不靠肉眼：实际输出 diff = 0.0000 rem。）
4. **回绕加了动效**。整分时 59.99s → 0s 原来是"啪"地由满变空。
   现在加第三条 path `ring-flash`：回绕后 650ms 内让满圈从 45% 淡到 0，
   于是有了「走满 → 消退 → 重新长起」的呼吸感。
   这一层用 JS 逐帧写 `opacity`，**不用 CSS animation** ——
   SVG 元素上的 CSS 动画在 Safari 9 上没把握，而这里本来就有逐帧循环可用。

**走秒带的第二轮修正（用户反馈"视觉上仍不等距"）**

用户是对的，而且这次暴露的是**我的校验方法本身有错**。

上一版我按「卡组 9.12rem」算间距 —— 但那是**含卡片左右外边距（各 0.23）的 flex 盒宽度**。
卡片的**可见灰边**外侧各有 0.23rem 外边距，所以可见卡组只有 **8.66rem** 宽。
从 flex 盒边界量会比从灰边量**多出 0.23rem**，于是"左右 0.30 / 上下 0.30"
这个看起来很漂亮的结果，实际是**左右 0.53 / 上下 0.30**。
校验脚本用了错误的基准，所以给出了假通过。

按用户给的三个应相等量重推（目标间距 = 两页之间的黑边 = **0.46rem**）：

```
环盒高 = 3.1  + 2×(0.46 + 0.09)        = 4.2rem
环盒宽 = 9.12 + 2×(0.46 + 0.09 − 0.23) = 9.76rem   ← −0.23 就是卡片外边距
圆角   = 卡片圆角 0.42 + 间距 0.46 + 半描边 0.045 = 0.925rem
```

圆角同样是**推导量**。上一版给的 0.55rem 比它小得多，四角被"收紧"，
直边间距正常、拐角更窄 —— 这正是用户看到的"圆角偏大 + 不等距"的**同一个根源**
（圆角给小反而转折更急，视觉上会被读成"弧度不对"）。

校验脚本已改成**从可见灰边量**，并把三个量写成断言：

```
L/R gap 0.4600 rem | T/B gap 0.4600 rem | inter-card 0.4600 rem   ✓
corner r == card_r + gap + stroke/2  [want 0.925 got 0.925 rem]   ✓
```

**刷新率**：从 `setInterval`（20fps）改成 **`requestAnimationFrame`**。
rAF 跟着屏幕刷新走，iPad 上跑满 60Hz；而 `setInterval` 与 vsync 不同步，
在高刷显示器上反而会看出拍频/抖动。帧循环**只在 v3 样式下运行**，
由 `applySettings` 里的 start/stop 控制，切走就停。

**走秒带的第三轮（视觉平衡 + 整体放大）**

1. **上下间距比左右小 0.05rem。** 上一轮把横纵都做成 0.46rem（数学等距），
   用户反馈"上下的黑边稍大一点"。这是**等宽间距在扁长构图里的视觉偏差** ——
   数学相等不等于视觉相等。纵向改为 `0.41rem`（R≈86 下约 4px，正是"几个像素"的量级）。
   **圆角必须跟着拆成椭圆弧**：间距既然不等，同一个半径就不再是等距偏移了：
   ```
   rx 92.5 = 卡片圆角 42 + 横向间距 46 + 半描边 4.5
   ry 87.5 = 卡片圆角 42 + 纵向间距 41 + 半描边 4.5
   ```
   这样拐角处的间距仍然均匀。

2. **整体放大 14%。** v3 是**高度受限**的：宽向允许 `R≈92`，高向只到 75。
   所以先给 v3 单独收紧竖向占位 —— 上下间距 `1.2 → 1.0rem`、
   舞台底部留白 `1.2 → 0.6rem`，竖排从 `8.1rem` 收到 `7.7rem`；
   再把 v3 的高度系数从 `0.098` 提到 `0.112`，**R 从 75.3 → 86.0（+14%）**。

   校验脚本里为此**新增了适配断言**（横竖屏各算一遍，确认不溢出、环不压到文字栏）：
   ```
   横屏  R=86.0  竖排 662/716px  环宽 840/1024  到文字栏余量 43px
   竖屏  R=66.0  竖排 509/984px  环宽 645/768   到文字栏余量 33px
   ```
   放大之后溢出是最容易出的事，而光看代码看不出来 —— 必须算。

**走秒带第四轮（五处微调）**

1. **时钟落到屏幕正中。** 之前偏高 0.6rem，是两件事叠加：`.stage` 的 `padding-bottom`
   把整组上推，以及 —— 更根本的 —— **居中的本来就是「日期+时钟+天气」整组，
   而时钟不是整组的几何中心**（它偏上 0.28rem）。
   改成让**时钟**居中，`padding-top` 是推导量：
   ```
   P = 栏总高 − 2 × 时钟中心距组顶 = 7.38 − 2×3.41 = 0.56rem
   ```
   ⚠️ 竖向任何一栏的高度变了都要重算。
2. **卡片整体缩小约 4%**：`4.1×3.1 → 3.95×2.98rem`，字号 `2.75 → 2.64rem` **等比跟缩**
   （只缩卡片不缩数字的话，数字在变小的卡里占比反而更大）。`.card` 是三样式共用的，
   所以 v1/v2 也会跟着小 4%。
3. **走带盒子完全不变，只重算曲率。** 黑边因此变大：横 `0.46→0.61`、纵 `0.41→0.47`。
   圆角必须跟着间距走（`rx 107.5 / ry 93.5`）—— 若沿用按旧间距算的 `92.5/87.5`，
   拐角会停在旧间距而直边已是新间距，**又变成"直边正常、拐角更窄"**（就是前几轮那个坑）。
   所以"走带不变"落地为**盒子尺寸不变**：校验里专门有一条断言守它。
4. **上下两条文字栏缩小**：字号 `.68→.60rem`，栏高 `1.0→.92` / `1.6→1.48rem`，
   高低温字号 `.55→.49rem`。
5. **齿轮贴到最右上角**（`.4 → .1rem`，面板同步），**空闲环再压暗一档**
   （深色 `#242424→#1a1a1a`，浅色 `#e0e0e0→#e4e4e4`）。

**已知副作用**（用户确认接受）：横间距 `0.61` 不再等于两页之间 `0.46`，
「三量相等」这条规则正式作废；横纵差也从 `0.05` 拉到 `0.14`。

**本轮新增的两条断言**（都是最容易悄悄写错的地方）：
- **时钟中心 = 屏幕中心**：用新栏高重算 `padding-top`，`want 0.56 got 0.56` ✓
- **走带盒子尺寸不变**：`9.76 × 4.10` ✓

**走秒带第五轮（恢复等宽 + 降低存在感 + 发丝线兜底）**

1. **黑边恢复成「横 = 两页之间」。** 卡片尺寸不动（`3.95×2.98`），改的是走带盒子：
   ```
   环盒宽 9.42rem = 8.82 + 2×(0.46 + 0.07 − 0.23)   横向间距 0.46 = 两页之间
   环盒高 3.94rem = 2.98 + 2×(0.41 + 0.07)          纵向间距 0.41（仍比横向小 0.05）
   ```
   （第四轮为了满足"走带不变"，盒子留在 `9.76×4.1`，导致横间距涨到 0.61。这轮缩回来。）

2. **降低走带存在感**：描边 `9 → 7` 单位，进度带配色 `#c8c8c8 → #a4a4a4`
   （浅色主题 `#4a4a4a → #767676` —— 浅底上不能压太深，否则比大钟还抢眼）。
   ⚠️ **描边宽度是环盒与圆角的输入**，改它必须一起重算：
   ```
   rx 91.5 = 卡片圆角 42 + 横向间距 46 + 半描边 3.5
   ry 86.5 = 卡片圆角 42 + 纵向间距 41 + 半描边 3.5
   周长回落值 2491
   ```

3. **iPad 上"空白时有一条细线"的兜底。** 判断是**零长度虚线**的渲染差异 ——
   有些引擎会给长度恰好为 0 的虚线画出一条发丝线，桌面引擎不画，正好对上
   "iPad 有、电脑没有"。对策：绘制长度短于约一个设备像素时直接 `visibility:hidden`，
   只影响每分钟开头 ~40ms，肉眼无感。
   ⚠️ **这条无法在桌面复现，只能上机确认**；若不奏效说明是别的原因。

**本轮新增断言**：**viewBox 宽高比必须等于 CSS 盒子宽高比**（本次 `2.3909 = 2.3909`）。
两者不一致会 letterbox，是发丝线这类渲染怪象的温床。

**走秒带第六轮（配色再压一档）**

纯配色改动，**不触碰任何几何量**（环盒、圆角、描边、周长回落值全部未动）。

配色演进表（**要回退直接照数值改**）：

| 元素 | 初版 | 第五轮 | **本轮** |
|---|---|---|---|
| 底衬环（深色） | `#242424` | `#1a1a1a` | **`#151515`** |
| 进度带（深色） | `#c8c8c8` | `#a4a4a4` | **`#7a7a7a`** |
| 底衬环（浅色） | `#e0e0e0` | `#e4e4e4` | **`#e6e6e6`** |
| 进度带（浅色） | `#4a4a4a` | `#767676` | **`#9a9a9a`** |

要点：
- 按「与背景的对比度」各降一档 —— 深色底进度带约 **48%**（原 64%），浅色底约 **60%**（原 46%）。
- **方向相反**：深色底往黑里压，浅色底往白里提。浅底上用深灰会显脏，必须是浅灰。
- **`ring-flash` 必须与 `ring-fill` 同色** —— 它是整分回绕时那层满圈淡出，

**走秒带第七轮（间距统一到 0.56 + 呼吸动效 + 文字栏再缩一号）**

1. **卡片再缩一档，两卡之间的黑边真的变宽了。**
   ⚠️ 关键是：**缩小卡片本身不会让两卡之间的黑边变宽** —— 那个宽度由卡片**外边距**决定
   （两卡之间 = 2×外边距）。要它变宽必须同时加大外边距：
   ```
   卡片   3.95×2.98 → 3.80×2.88（数字 2.64→2.56 等比跟缩，圆角 .40→.38）
   外边距 0.23 → 0.28   ⇒   两卡之间 0.46 → 0.56
   ```
2. **走带四个方向的间距全部 = 0.56**（不再保留"纵向比横向小 0.05"的微调）。
   间距既然相等，圆角也相等，**不再需要椭圆弧**：
   ```
   圆角 97.5 = 卡片圆角 38 + 间距 56 + 半描边 3.5
   环盒 9.42 × 4.14rem · viewBox 942×414 · 周长回落 2517
   ```
3. **已走部分更淡**：深色 `#7a7a7a → #5c5c5c`，浅色 `#9a9a9a → #adadad`。
4. **未走部分加呼吸动效**：一秒一个周期，**整秒最亮、中途最暗** ——
   相位这么选是为了和秒针的节拍对上，跳秒那一刻亮一下。
   ```
   opacity = 0.15 + 0.85 × (0.5 + 0.5·cos(小数秒 × 2π))
   ```
   逐帧写，复用已有的 rAF 循环。已走部分盖在它上面，所以动效只作用在没走到的区段。
   ⚠️ 为此把底衬环**从上一版的 `#151515` 调亮到 `#1e1e1e`**
   （浅色 `#e6e6e6 → #dfdfdf`）—— 太暗的话 0.15~1.0 的透明度变化根本看不出来。
   **这是刻意的回退**，与第六轮"更贴近背景"的方向相反，原因是它现在要承载动效。
5. **文字栏再缩一号**：字号 `.60 → .54rem`，栏高 `.92→.83` / `1.48→1.33rem`，

**走秒带第八轮（呼吸降频 + 走带压到"只是暗示"）**

1. **呼吸周期 1 秒 → 2 秒**：`cos(小数秒 × π)`（原来是 `× 2π`）。
   偶数整秒最亮、奇数整秒最暗。周期拉长是为了更像背景的一点起伏，而不是在"闪"。
2. **已走部分再压一档**：
   ```
   深色 #5c5c5c → #3a3a3a（22.7%）   浅色 #adadad → #c4c4c4（76.9%）
   ```
   用户点名要"只是起到暗示作用"。

   ⚠️ **底衬环（未走部分）没有跟着压** —— 它承载呼吸动效，
   太暗的话 `0.15~1.0` 的透明度变化就白做了。**所以只压"已走"部分。**

   校验里为此加了一条**结构性不变式**：已走部分对背景的对比度必须大于
   未走部分的峰值，否则分不出"走过没走过"。两个主题都成立：
   ```
   深色  fill 22.7%  vs  track 11.8%
   浅色  fill 76.9%  vs  track 87.5%   （浅底 #e9e9e9，"更显眼"= 离底色更远）
   ```

**走秒带第九轮（删底衬环 + 插冒号做 1Hz 呼吸）**

1. **删掉「未走部分」（底衬环）**，只保留已走部分。挂在它上面的那个两秒周期呼吸
   也一并移除 —— SVG 里的 path 从 3 条减到 **2 条**（progress + flash）。
   「暗示秒数」的职责转交给下面的冒号。
2. **两卡之间插入冒号**：
   - 用**字体自带的「:」字形**，字号与数字相同（`2.56rem`）——
     字重和比例天然一致，不用自己画圆点去凑
   - **1Hz 呼吸**：`opacity = 0.20 + 0.80 × (0.5 + 0.5·cos(小数秒 × 2π))`，
     整秒最亮、中途渐灭，和秒针节拍对上
   - 只在 v3 样式显示（`body.style-v3 .colon`）
3. **关键是它没有把整套尺寸带偏。** 冒号插在两卡之间，但把 `#hh` 的右外边距和
   `#mm` 的左外边距从 `.28` 收到 `.08`，中间刚好放 `.40` 宽的冒号：
   ```
   #hh mr .08  +  冒号 .40  +  #mm ml .08  =  .56   ← 与原来的 .28 + .28 相同
   ```
   ⇒ **卡组 flex 盒宽度不变（8.72rem）** ⇒ 环盒 / 圆角 / 周长回落值 /
   根字号系数 / 居中 `padding-top` **全部不用动**。
   校验里专门有一条断言守这个（`clock flex box: now 8.72 | before 8.72`）。

**走秒带第十轮（冒号改用纯图形 —— 字形方案实机不可见）**

上一轮用字体自带的「:」字形，**实机上完全看不到冒号**。改成两个 CSS 圆点。

**字形方案为什么会失败**（两条，第二条是主因）：
- 字体栈是 `Menlo → JetBrains Mono`，**iPad 落 Menlo、电脑落 JetBrains Mono**，
  两家冒号字形本来就不同 —— 跨设备不一致是必然的
- 更根本：字形**步进宽 `0.6em ≈ 1.54rem`**，而这个槽只有 **`0.40rem`**。
  只能靠 `text-align:center` 把一个**溢出槽宽的**字形居中 —— 这个行为依赖
  引擎实现，一旦它不按预期居中，墨迹就落到槽外、被相邻的卡片盖住。

**现在**：两个 `<i>` 圆点，直径 `.30rem`、间距 `.36rem`（合计 `.96rem`，卡片高 `2.88rem`）。
直径 / 间距 / 位置全部可控，**与字体和引擎都无关**。
校验里为此加了一条"没有字体依赖"：`.colon` 规则里不允许再出现 `font-family`。

槽宽 `.40` + 两侧外边距 `.08 × 2` = **`.56rem` 不变**，所以**走带几何仍然一点没动**。

**走秒带第十一轮（冒号推广到三种样式 + 做成设置项）**

1. **三个样式都有冒号了**：
   | 样式 | 冒号数 | 位置 |
   |---|---|---|
   | v1 平衡 | **2 个** | 时∣分、分∣秒 |
   | v2 层次 | **1 个** | 时∣分 |
   | v3 走秒 | 1 个 | 时∣分 |
   为此加了第二个冒号元素 `#colon2`，只在 `body.colon-on.style-v1` 下放出来。
2. **布局一点没动。** 冒号仍然插进**原有间隙**：把相邻的卡片外边距从 `.28` 收到 `.08`，
   中间放 `.40` 的冒号。三种样式的卡组 flex 盒宽度都保持不变，校验里逐条断言：
   ```
   v1 平衡  2 个冒号  13.08 → 13.08
   v2 层次  1 个冒号  11.18 → 11.18
   v3 走秒  1 个冒号   8.72 →  8.72
   ```
   ⇒ **走带几何、根字号系数、居中 `padding-top` 全都不用动**（这是这套做法的全部意义）。
3. **做成设置项**：设置面板多了第 4 行「冒号　开/关」，默认**开**，持久化到 localStorage。
   整套冒号规则改挂到 `body.colon-on` 上 —— **关掉时那些规则一条都不生效**，
   卡片外边距回到 `.28`，布局与"加冒号之前"完全一致，**不会留下一段 0.40rem 的空洞**。

⚠️ **顺带修了一个门闸 bug**：帧循环原本只在 v3 样式下跑（那是为走带设计的），
但冒号呼吸在 v1/v2 下也要跑。改成 `v3 || colon` 启动，
`updateRing` 的提前返回条件也同步放宽 —— 否则勾了冒号但在平衡/层次样式下，

**走秒带第十二轮（冒号呼吸：翻转相位 + 曲线改成"圆角方波"）**

1. **相位翻转**：整秒时**最暗**（原为整秒最亮），中途最亮。
2. **曲线不再用正弦。** 用户指出：正弦在高低两端一路平滑，人眼读不出"亮"和"灭"
   是两个**状态**。改成「棱角被圆滑化的方波」：
   ```
   [0, PLAT)                   平顶在 0（灭）
   [PLAT, PLAT+RAMP)           smoothstep 升到 1
   [PLAT+RAMP, 2·PLAT+RAMP)    平顶在 1（亮）
   [2·PLAT+RAMP, 1)            smoothstep 降回 0
   其中 PLAT = 0.32、RAMP = 0.18
   ```
   **选 smoothstep 是有理由的**：它两端的斜率恰为 **0**，与两侧平顶无缝相接 ——
   这正是"方波的棱角被圆滑掉"的数学形式。若用线性过渡，会留下两个折角。

   **数值验证**（把曲线移植到 Python 采样 4000 点）：
   ```
   平顶        32% + 32% = 64% 的时间精确处于 0 或 1
   明确状态    圆角方波 74%  vs  正弦 29%   ← 差 2.55 倍，两个状态分得开
   端点斜率    0.0093（≈0）→ 无折角
   其他        连续、单调、p=1 与 p=0 无缝回绕、值域恰为 0..1
   ```

**走秒带第十三轮（冒号相位对齐整秒）**

要求：**冒号最亮的一瞬间 = 秒数跳变的那一瞬间**。

> ⚠️ 这与上一轮的"翻转"方向相反 —— 上一轮做成整秒**最暗**，这一轮翻回来做成整秒**最亮**。
> 交付时已把这个冲突讲明，按最新要求实现。

**做法：曲线形状一点没动，只整体平移相位。**
未加偏移时"亮"的平顶落在 `[PLAT+RAMP, 2·PLAT+RAMP] = [.50, .82]`，中心在 `.66`。
要让整秒（相位 0）正好落在平顶**正中**，就把整体推移 `.66`：
```
PHASE = PLAT + RAMP + PLAT / 2 = 0.66
p = (小数秒 − floor(小数秒) + PHASE) mod 1
```

**数值验证**（采样 4000 点）：
```
frac=0    → beat = 1    最亮   ← 秒跳变那一刻
frac=0.5  → beat = 0    最暗
亮平顶跨 frac [-0.16, +0.16]，关于整秒对称
暗平顶居中在 frac 0.50
平顶长度仍是 32% / 32%   ← 形状没变，只是平移
过渡段端点斜率 ±0.0093（≈0）→ 圆角完好
过渡段中点斜率 8.33      ← 确实是真过渡，不是硬切
```

⚠️ `PHASE` 是从 `PLAT` / `RAMP` **推导**出来的（`PLAT + RAMP + PLAT/2`），不是写死的魔数 ——
以后调 `PLAT` 时对齐关系会自动保持，不会悄悄错位。

**走秒带第十四轮（冒号相位再翻转：整秒最暗）**

与第十三轮方向相反，翻回来了。**曲线形状一点没动，只改 `PHASE` 一个常量。**

为了让"翻来翻去"变成一行的事，两种相位都写成了从 `PLAT`/`RAMP` 推导的形式，
并且都留在代码注释里：

```
整秒最暗（暗平顶居中） → PHASE = PLAT / 2                = .16   ← 当前
整秒最亮（亮平顶居中） → PHASE = PLAT + RAMP + PLAT / 2  = .66
```

数值验证：
```
frac=0   → 0   最暗   ← 秒跳变那一刻
frac=0.5 → 1   最亮
暗平顶跨 [-0.16, +0.16]，关于整秒对称
亮平顶居中在 frac 0.50
平顶长度仍 32% / 32%，端点斜率 ≈0（圆角完好），连续且无缝回绕
```

**走秒带第十五轮（找到"怎么调都对不齐"的真正原因）**

用户反馈：**无论把冒号相位往哪边翻，都跟"新秒出现"对不齐**，而且上一次某个相位
看起来是"完美"的。翻了三次都不对 —— 说明问题不在相位。

**根因不在冒号，在秒显示的更新节奏上：**
```
秒显示：setInterval(tick, 250)   ← 每 250ms 轮询一次
```
秒数字最多比真实时间**晚 250ms**（平均 125ms）才跳；而冒号的相位是按**真实时间**
（`getMilliseconds()`）算的。两者天生差一个 **0~250ms 的固定偏移** ——
无论怎么翻冒号相位，都只是在"提前"和"更晚"之间挪，**永远对不齐**。
用户某次看到"完美"，是那个偏移恰好很小。

**关键量化**（这是判断"能不能对齐"的依据）：
```
冒号亮平顶只跨整秒前后各 160ms
旧轮询滞后 0~250ms（平均 125ms）   ← 量级和整个平顶相当
```
所以对齐与否基本是碰运气 —— 这也解释了为什么"上一次"碰巧对了。

**修法：让秒显示贴住整秒，而不是改冒号。**
```js
function scheduleTick() {
  var ms = new Date().getMilliseconds();
  setTimeout(function () { tick(); scheduleTick(); }, 1000 - ms + 8);
}
```
每次对齐到下一个整秒后 8ms 触发。**残余误差从平均 125ms 降到 8ms**，
而亮平顶有 ±160ms 宽 —— 数字跳变稳稳落在平顶正中。
顺带把轮询从 4Hz 降到 1Hz，功耗也更低。

同时把冒号相位设成用户要的「整秒最亮」（`PHASE = PLAT + RAMP + PLAT/2`）。

**走秒带第十六轮（视觉对齐：对齐点从"最亮"改到"上升途中的 66%"）**

用户反馈：**数字对齐了，但视觉没有**，并建议冒号做一个偏移延迟。

**这条指出了我前几轮的一个概念错误。** 我一直让"平顶中心"（最亮那一刻）
对齐整秒 —— 但**眼睛感知的"闪"发生在亮度【变化】最明显的时候，不是最亮的时候**。
平顶中心对齐整秒 ⇒ 整秒时它已经亮了一段时间 ⇒ 感知上自然偏早。

改成让**上升段上亮度达到 66% 的那一刻**对齐整秒（用户建议的值）：
```
smoothstep(t) = t²(3−2t)，t = 0.61 时 ≈ 0.662
PHASE = PLAT + ALIGN_T × RAMP = 0.32 + 0.61×0.18 ≈ 0.43     （原 0.66）
```

数值验证：
```
整秒那一刻：亮度 0.662、斜率 +7.9    ← 正在上升，正是感知到"闪"的时刻
同一个 66% 点在旧相位下落于 frac 0.770 → 比整秒早 0.23 秒
                                        ↑ 这 0.23 秒就是"视觉偏早"的全部来源
全亮在整秒后 0.070 秒到达
平顶长度（32%/32%）、连续性、无缝回绕均未变
```

要调就动 `ALIGN_T`：调小 → 对齐点更靠"刚亮起"（感知更早）；调大 → 更靠"已经很亮"。

**走秒带第十七轮（新增：日出日落自动切主题）**

**先验证 API 能力：Open-Meteo 支持**，而且能在**同一个天气请求里**拿到，不用多发一次：
```
&daily=temperature_2m_max,temperature_2m_min,sunrise,sunset
→ sunrise ['2026-10-02T06:14', ...]   sunset ['2026-10-02T18:09', ...]
```
返回的是**本地时间**（`timezone` 参数已生效），不用自己做时区换算。

**实现要点**

- **解析**：手动拆字段用 `new Date(y, m-1, d, h, mi)` 构造，**不用 `new Date(字符串)`** ——
  ES5 与 ES6 对"无时区的日期时间串"的解释不一致，各家引擎也不同；手动构造语义永远明确。
- **判定**：日出后浅色、日落后深色。`readSun()` 会在 `sunset <= sunrise` 时**拒绝**（脏数据保持 null）。
- **取不到就整体不动作**（接口失败 / 极区无日出），保持用户当前主题 ——
  宁可不同步，也不要拿错时间把主题切错。

⚠️ **只在昼夜状态【发生变化】时才动作**，不是每次检查都套用。
否则用户手动切的主题会被下一秒立刻覆盖回去，那个按钮就形同虚设。
手动切过之后，自动逻辑要等到下一次日出/日落才重新接管。

另外 `autoThemeTick()` 里**不调 `applySettings()`**：主题只影响颜色，不需要重算
layout / 环几何；而且 `applySettings()` 末尾会调 `tick()`，从 `tick` 调过来会形成重入。

设置面板新增第 5 行「自动主题　开/关」，**默认开**，持久化。
面板总高 `1.85 + 5×0.98 + 0.52×2 = 7.79rem`，横屏 670px，768 内放得下。

**验证**（用真实日出日落时间模拟昼夜判定）：
```
深夜→dark  日出前一分钟→dark  日出那一刻→light
正午→light 日落前一分钟→light 日落那一刻→dark  深夜→dark
```

**走秒带第十八轮（自动主题与手动主题改为互斥）**

原先的设计是"手动选主题先赢，直到下一次日出/日落再被自动接管"。
用户要求两者**互斥** —— 这个更清楚，也避免"我明明选了、过一会儿它自己又变回去"的困惑。

改法：
- `setSetting` 里，**手动选主题 → 同时把 `autoTheme` 关掉**
- **打开自动主题 → `lastDayState = null`**，下一次 tick 立刻按当前昼夜套用
- 新增 `body.auto-theme` 类：自动开着时把**主题那一行压暗**，
  提示"此刻由日出日落接管、不由按钮决定"。按钮仍可点 ——
  点一下就自动关掉自动主题、并采用你选的那个。

`autoThemeTick` 里"只在状态变化时动作"那条**保留**：互斥之后它不再是"防打架"，
而是避免每次 tick 都重设主题类（无谓的 DOM 写入）。

**状态机模拟验证**（把真实逻辑照搬到 Python 跑一遍）：
```
auto 开 + 白天       → light
手动选 dark          → dark，且 auto 自动关闭
auto 关闭期间 tick   → 主题纹丝不动

状态不变时连续 tick  → 不重复套用
transitions: ['auto->light', 'manual->dark', 'auto=True', 'auto->light']
```

**走秒带第十九轮（天气：10 分钟刷新 + 破缓存 + 未来 1 小时）**

1. **刷新间隔 `20 → 10` 分钟。** 上游 Open-Meteo 的数据粒度是 **15 分钟**
   （实测 `current.interval = 900` 秒），拉取间隔比它短一点，陈旧度才不会被

   加之前**先实测了 Open-Meteo 对未知参数的反应 —— 返回 200、不报错**，
   所以这个参数是安全的。（不先验就加，万一上游对多余参数报错，会把天气整个搞挂。）

   - 用 `hourly=precipitation_probability,weather_code` 取；`forecast_days=2`
     保证临近午夜时"下一个整点"也在数组里
   - 匹配方式：**按时间字符串直接比较**。接口返回的 `time` 就是
     `2026-10-02T19:00` 这种本地时间串（timezone 已生效），

   - 找不到就留空，**不猜**

| 5 | **移除点击调暗**（误触成本高于收益），页面不再有任何触摸响应 |

**几个刻意的决定**

- **秒卡用真实尺寸减半，不是 `transform: scale(0.5)`**。
  缩放变换不改变布局盒子，`.clock` 算出的总宽不会变小，"重算总宽再整体居中"就无从谈起。
  实现是 `.card--sm` 修饰类（宽高字号圆角全部取半）+ `.clock` 的 `align-items: flex-end`。
- **箭头用 CSS border 三角画，不用 `↑` `↓` 字符**。那些字符在 Avenir Next 和苹方上的
  字重、基线位置不一致，跨设备观感不稳；三角的尺寸和颜色完全可控。
- **天气两栏都定宽**。左栏会被描述长度影响（「晴」1 字 ↔「晴间多云」4 字），
  不定宽的话整条天气栏会重新居中、产生可见位移。
- **透视值改用 rem**。原来写死 `160px` 是个潜在 bug ——
  屏幕越大卡片越大，而透视距离不变，畸变反而越夸张。
  改成 `20rem` 后透视距离约为卡高的 6.5 倍，且随卡片一起缩放。
  调法：文件里 10 处 `perspective(...)` 全改同一数值，**越大越平（越长焦）**。

**竖排预算**：日期栏 1.0 + 间距 1.2 + 时钟 3.1 + 间距 1.2 + 天气栏 1.6 = **8.1rem**
（v1 约 9.0rem，反而更松 —— 文字栏虽然翻倍，但两个间距从 1.35rem 收到了 1.2rem）。
时钟总宽 **11.63rem**（v1 是 13.68rem）。两条约束都松了，
所以根字号系数从 `0.064w` 提到 `0.067w`，整体放大一点。

**v2 唯一需要真机确认的点**：`perspective()` 里用 `rem` 是否被 Safari 9 接受
（理论上没问题，它就是个长度单位）。若翻转异常，退路是在 JS 的 `layout()` 里算成 px 写进去。

**关键决定与原因**

- **不用 `-apple-system`**：iPad 2 上它给的是 SF 还是 Helvetica Neue 无法确认（Apple 给 A5 老设备做过"核心版" iOS 9）。写死字体名消除不确定性。
- **卡片是 1.32:1 横长方形，不是参考图的近正方形**：参考图那款字体是**窄体比例字体**（数字宽约 0.45em），
  而 Menlo / JetBrains Mono 是**等宽**（0.6em）。等宽下要保住正方形卡片，数字只能缩到卡高 50%，
  会失去气势。选择"数字优先"。若要恢复正方形，需换 Roboto Condensed / Archivo Narrow 这类窄体。
- **秒位不翻页**：这台设备要跑几年，秒位翻页意味着 50% 的时间在动画中。
- **调暗用独立遮罩层**，不是给容器加 `opacity`——后者会建立 grouping context，
  把整棵子树压成单个合成层，翻页每一帧都要重新光栅化，A5 上很吃亏。

**踩过的坑（改代码前必读）**

1. **iOS 9 不支持 WOFF2**（需 iOS 10+），会**静默忽略**并回退到系统字体，
   不报错、控制台无提示。必须用 WOFF 或 TTF。
2. **iOS 9 不信任 Let's Encrypt 的根 ISRG Root X1**（iOS 10 才进信任库）→
   跨域 XHR 到使用 LE 证书的站点会**静默失败**：页面正常、数据永远为空。
   症状是「iPhone 正常、iPad 空白」。解法是 `_redirects` 里的 200 rewrite 同源代理。
3. **`backface-visibility` 必须带 `-webkit-` 前缀**（Safari 9–15.3 都要求），
   而 `transform` / `perspective` / `animation` 在 iOS 9 已无需前缀——和直觉相反。
4. **3D 透视写进 `transform` 的 `perspective()` 函数**，全程不用 `preserve-3d`。
   否则会被祖先的 `overflow` / `opacity<1` / `filter` 压平成 flat，翻页失效。
5. 字体目录里的 3 个 TTF 是从系统那份**可变字体** `JetBrainsMono[wght].ttf`
   用 `fontTools.varLib.instancer` 派生的**静态实例**。
   可变字体自身需要 iOS 11+，直接拿来用 iOS 9 只会渲染默认字重、且粗体退化成伪粗体。

**已知的未解细节**

- PC 预览和 iPad 实机字形不同：Windows 没有 Menlo，会落到 JetBrains Mono ExtraBold。
  想让两边一致，把 `.card` 的 `font-family` 里 `'JetBrains Mono'` 提到 `Menlo` 前面。
- 整块内容竖向只占屏幕约 70%（宽度是瓶颈，三张卡横排已顶到边），4:3 的竖向空间没用满。

**总开关**（`index.html` 里 `.card` 那几行）

```css
font-family:Menlo,'JetBrains Mono',monospace;   /* 字体 */
font-size:2.75rem;                              /* 数字大小 */
width:4.1rem; height:3.1rem;                    /* 卡片比例 */
border-radius:.42rem;                           /* 圆角 */
```
